The generation of the TU Delft Prometheus' flame was shown in a previous section of the wiki: **3. Path Planning**. In this chapter, the implementation of this path to the real 3D world in Gazebo is described.

As the problem is now 3-dimensional, it is important to establish the correct orientation of the coordinate frames with respect to each other. While the drones are programmed in the NED (North-East-Down) frame as mentioned before in the wiki, the Gazebo world uses the ENU (East-North-Up) frame, which requires some adjustments to the frame pathing as described earlier. The reasoning behind this is described here:

1. The flame model is centred around the coordinates of [x,y] = [12.5,3.5] (m) in the Gazebo world frame.
2. This corresponds to the NED-frame coordinates of [x,y] = [3.5, 12.5] in the drones' coordinate frames.
3. Although this change is small, the transition might be more complicated for more difficult paths that use three dimensions.
3.a If this is the case, it would probably be useful to come up with a generalised transfer function between these coordinates, but for the purposes of this flame path implementation, a simple logical change is sufficiently effective.
4. Moreover, due to the orientation of the flame in the 1st quadrant of the coordinate system, the flame path has to be flipped on the x-axis (moving towards the negative direction).

The following line was thus integrated into the former flame path:
```powershell
flame_points_x = -flame_path[:,0] # x-coordinates in the NED frame
```

## Implementation of the flame path to the Gazebo 3D world

In order to integrate the flame path into the rest of the pathing to and from the flame, the function of **updated trajectory** is created. This includes the following functions:

1. Adding a time delay based on the follower drone order

```powershell
def updated_trajectory(self, setpoints: list, follower_number: int, dt: float) -> list:
        # TIME DELAY
        extra_points = 10*follower_number/dt # add a time delay in seconds (assuming a 10Hz timer for dt)

        # Add extra points to the front of the setpoints to create a delay
        new_points = []
        for i in np.arange(extra_points):
            new_points.append([self.coordinate_transform[0], self.coordinate_transform[1], self.takeoff_height])
```
Here, the x and y coordinates of the extra points are taken to be the coordinate transform components of the respective drone. But why is this done? - This had to be done because once the drones start flying, the difference in the coordinate transforms will automatically be deducted from the assigned target locations in order to have the drones fly uniformly with respect to the leader's local frame. As we want to have the follower drones initially hover at their respective starting locations, the coordinate transform had to be artificially added as the target coordiante, in order to subrtract it later on when interpreting the input coordinates. This was found to be the easiest way to do this; the other potential implementation could have utilised manually adjusting the sections of the flight where the coordinate transforms are applied. However, this potential implementation would not be as robust in case the length of the time delay was adjusted, for example.

2. The path to the location of the flame pattern would then be created as a series of straight lines along the x- nad y-coordinates at a constant altitude of -2m (the default take-off altitude):

```powershell
        # Add a path to the big flame model in the custom world
        path_to_flame = [[0.0,1.0, self.takeoff_height]]

        section_1_length = 3.5
        section_1_x_points = np.linspace(0.0, section_1_length, 7) ## first path section with 0.5m increments
        for x in section_1_x_points:
            path_to_flame.append([x, 1.0, self.takeoff_height])
        
        section_2_length = 9.0
        section_2_y_points = np.linspace(1.0, section_2_length, 21) ## second path section with 0.5m increments
        for y in section_2_y_points:
            path_to_flame.append([section_1_length, y, self.takeoff_height])
```

3. With the path to the flame location constructed, the next step is to implement the 2D flame trajectory in the 3D space and orient it to the xz-plane. This is handled by the following code snippet, which deconstructs the existing path points and assigns them to the x- and z-axes. Additionally, the origin of the flame path and the take-off altitude have to be accounted for in this assignment of coordinates. Moreover, the y-axis location of the points remains constant throughout the trajectory and is performed parametrically with the section_2_length. All of this is performed as follows:
```powershell
        setpoints_x = [point[0] + section_1_length for point in setpoints]
        setpoints_y = [ section_2_length for point in setpoints]
        setpoints_z = [-point[1] + self.takeoff_height for point in setpoints]
```

4. The setpoints are then restacked to three columns and converted to a list to be called later when the trajectory setpoints are forwarded to the drones during the simulation:

```powershell
        setpoints = np.stack((setpoints_x, setpoints_y, setpoints_z), axis = 1)
        setpoints = setpoints.tolist()  # Convert to list for concatenation```

5. And finally, the return path (which is the reverse of the path to the flame) is created, and all of the path sections are added together: 
```powershell

        #The path back from the flame is the reverse of the path to the flame
        path_to_start = path_to_flame[::-1]  # Reverse the path to the flame
        
        # Concatenate the new points to the front of the setpoints
        setpoints = new_points + path_to_flame + setpoints + path_to_start
        return setpoints
```

Once the drone has taken off (first 100 ticks of the simualtion), this path will be followed through the following implementation:

```powershell
        if self.offboard_setpoint_counter >= 100:        
            if self.position_change < len(positions):    
                target_x = positions[self.position_change][0]
                target_y = positions[self.position_change][1]  
                target_z = positions[self.position_change][2] # z is negative in NED frame
                # Telling to move to the next position after the first has been reached
                

                # Adding the offset if it is a follower drone 
                if self.leader != "":
                    offset_x = self.coordinate_transform[0] 
                    offset_y = self.coordinate_transform[1]
                else:
                    offset_x = 0.0
                    offset_y = 0.0
````
The drone will receive the next waypoint target if it has reached sufficiently close to the previous target point, determined by the following code:

```powershell
                if np.abs((self.vehicle_local_position.x + offset_x) - target_x) < margin and \
                        np.abs((self.vehicle_local_position.y + offset_y) - target_y) < margin and \
                            np.abs(self.vehicle_local_position.z - target_z) < margin:
                    self.position_change += 1
```
Where offset is the coordinate transform between the follower and the leader, and **margin** is the accepted positional inaccuracy of the drones.
