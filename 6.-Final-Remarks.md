## Light functionality

The PX4-Autopilot base already includes the relevant topic of LEDControl, which was attempted to be used during the project. Even though this was implemented to its full extent with the addition of a custom topic assigning a colour depending on the drone's role in the simulation (leader, follower, follower order), it did not yield an actual light display in the simulation due to the used x500 drone not having a light onboard its Gazebo model.

The manual addition of a light to the model was also attempted, but abandoned after multiple tries yielded errors on the GitHub synchronisation side due to git submodules. As a result of these endeavours and the limited time frame of this project, the idea of having lights aboard the drone was discarded in favor of investigating the potential implementation of data structures such as tf trees and behaviour trees.

It is recommended to add a custom PX4 model for Gazebo built on the foundation of existing model to incorporate the physical light function in the simulation. This can be done by:
1. Modifying the model.sdf file in PX4-Autopilot/Tools/simulation/gz/models/x500/ to include a visual light element (e.g. a <light> or glowing <visual>).
2. Ensure a plugin is included in the SDF (or added to the PX4-Gazebo interface) that listens to the led_control uORB message and updates the light color or state accordingly.

## Behaviour Trees 
Currently a behaviour tree is implemented to define the elements of the trajectory such as take-off, the flame outline and landing again. Behaviour trees are also very useful for implementing fail-safe options. If more time could be committed to this project, it is recommended to implement the following fail safe modes:

PX4 has its own failsafe protocol incorporated in its firmware. When the failsafe is activated, it will be shown in the `VehicleStatus`uORB message. A behaviour tree can be used to determine how the rest of the swarm should respond [[1]](https://docs.px4.io/main/en/msg_docs/VehicleStatus.html). 

One way the failsafe mode could be activated is if there is a sensor failure. Within the `VehicleStatus` uORB message, there is the `failsafe`, `system_failure`and `condition_system_sensors_initialized` which will tell you if failsafe has been activated, if there is a critical system false and if a sensor doesn't work or is missing. In newer PX4 versions, you can use `subsystem_health` to find which sensor is degraded. Using these message attributes, the behaviour tree can be used reassign leader and follower trajectory setpoints.

In addition to this, it can also be used if the drone crashes due to an obstacle in the path. Crash detection can be done by analysing any sharp changes in vertical position and/or attitude along with actuator commands vs position change using the uORB messages `vehicle_local_position`, `vehicle_attitude` and 'actuator_outputs'. An extra part of the sequence in addition to the restructuring of the swarm would be to first recalculate a new trajectory around the obstacle. This would require some sort of object detection such as using a LiDAR, depth camera, etc to know where the trajectory setpoints are in 3D space.

## Creating an Alternative Follower Mode

The current drone project uses the leader-follower relationship to determine the flight path in a uniform coordinate frame. In this instance it is performed by all of the drones knowing the required path they need to take, with the follower drones needing to adjust their paths to align with the one of the leader through a transformation of the local coordinate frames. 

However, it would also make sense to include an alternative follower mode - one that does not require prior knowledge of the taken path ahead of time. This could be done by having one of the nodes record the real locations of the leader drone as it flies through the predetermined circuit. Forwarding these coordinate points to the follower drone with some sort of time delay would result in the follower drone being able to follow a similar path behind the leader drone.

This alternative implementation of the follower drone would come with benefits and drawbacks:
Benefits:
- The follower drones do not require a list of the path points as part of their code, reducing the performed calculations.
- It might be simpler to perform the role of a follower of a follower using this role.

Drawbacks: 
- In case the leader drone stops along its path for a long enough period of time, the follower will eventually catch up and crash into the leader drone.
- An extra topic will have to be made to collect the recorded positions of the leader drone.
- Depending on the leniency of the positional accuracy margin, the follower drone might not be exact in following the desired path. 

3. Consideration to Real Life Application (Lauren)

In the case of the simulator, the coordinate transforms of the leader and follower local frames only account for changes in the xy-plane as the ground of the simulation is perfectly flat and thus there is never going to be a z-directional displacement between the reference frames. In the real world, however, this would have to be taken into account as the ground might not necessarily be perfectly flat and thus induce a difference between the coordinate frames in the z-direction. Luckily, the coordinate frames of the drones are always oriented in the NED (North-East-Down) direction, so no angular adjustments need to be implemented in the real case.
