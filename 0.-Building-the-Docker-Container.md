To build the Docker container, both a DockerFile and devcontainer.json file is needed. Both of these should be stored in a folder called .devcontainer in the desired location on your laptop. These two files are needed to create the development container. The DockerFile builds the environment (OS + tools + ROS + PX4) and the devcontainer.json file configures VS Code to connect to and use that environment.

## Why do we do this?
Creating a development container will allow anyone to access the same versions of software (such as ROS2 and Gazebo), same libraries (numpy, scipy, etc.) and all other external downloads needed (PX4 installations, Micro XCRE-DDS bridge, etc.) for a specific development project or overall to run an already existing simulation. It prevents each contributor from having incompatible or different versions of software and libraries so that everyone is working with the same tools. Then by building and opening in the container, the developer can use everything again as normal but without the stress of worrying about incompatibilities and about downloading specific packages/software that would be needed. 

In this specific project, we will need to ensure that everyone is working with Gazebo Ignition and ROS2 Humble. Additionally, all python libraries that would need to be used will be included along with all necessary downloads from the PX4 side, such as PX4 itself, the required drone models needed for Software-In-The-Loop (SITL) simulations and the Micro XCRE-DDS bridge to communicate between the drone and ROS2. 

This page will show you how to construct your DockerFile and devcontainer.json file for this specific application. After this, you can modify it anyway you like for your own specific project!

## Creating the DockerFile
To understand the basic configuration of a DockerFile, please watch this video before proceeding: \
[![Crafting your Dockerfile (Docker and Robotics Pt 3)](https://img.youtube.com/vi/RbP5cARP-SM/0.jpg)](https://www.youtube.com/watch?v=RbP5cARP-SM "Crafting your Dockerfile (Docker and Robotics Pt 3)")
### Base Setup: User and Workspace
This base setup starts us from an official ROS 2 Humble desktop image. ARG lets you switch ROS versions easily.

```dockerfile
ARG ROS_DISTRO=humble 
FROM osrf/ros:${ROS_DISTRO}-desktop AS ros_user_setup
```
### Creating a Non-Root User
Creating a root user would allow anyone to do anything on the system, including installing software, changing system files, or deleting everything (even by accident). The non-root user has limited permissions. It can run programs, edit files in their own space, but can't mess with system-critical stuff without sudo. Therefore, for security, a non-root user is created. 

```dockerfile
ARG ROS_USER=ros
ARG ROS_USER_UID=1000
ARG ROS_USER_GID=$ROS_USER_UID

```

After this step, the user is added to the system, installs sudo so the new-user can have admin tasks and sets it up to be passwordless for easy access.

```dockerfile
RUN groupadd --gid $ROS_USER_GID $ROS_USER \
    && useradd -s /bin/bash --uid $ROS_USER_UID --gid $ROS_USER_GID -m $ROS_USER \
    && apt-get update \
    && apt-get install -y --no-install-recommends sudo \
    && echo $ROS_USER ALL=\(root\) NOPASSWD:ALL > /etc/sudoers.d/$ROS_USER \
    && chmod 0440 /etc/sudoers.d/$ROS_USER 
```
The last step is to switch to this new user and make the ROS2 workspace.

```dockerfile
USER $ROS_USER
RUN mkdir -p /home/ros/ros2_ws/src
```
### Development Stage: Tools & Dependencies
This stage will start from the previous ROS image and built on it in a stage called the `dev` stage. It will stack the layers like LEGOs. 

First, start from the previous image like so:
```dockerfile
FROM ros_user_setup AS dev
```

What it will install are:
1. Build tools (e.g., build-essential, cmake)
2. Dev utilities (e.g., htop, vim, wget, ccache)
3. ROS-specific tools (e.g., colcon, rosdep)
4. Clean up after to keep the image light

This can be written as so:
```dockerfile
RUN sudo apt-get update && sudo apt-get install ...
```
Please refer to lines 29-54 to see what our installations are.

To add Python-based linters and formatters like `flake8`, `black`, `isort`, use:

```dockerfile
RUN sudo pip3 install ...
```

This can be seen from lines 57-63. 

To fix issues with numpy binary compatibility:
```dockerfile
RUN sudo pip3 install --no-cache --upgrade numpy
```

Lastly, to update ROS dependency database:

```dockerfile
RUN rosdep update
```

### Installing the Micro XCRE-DDS Agent
Clones and builds the Micro-XRCE-DDS Agent, which bridges the drone's controller software to ROS2. 

```dockerfile
WORKDIR /home/ros
RUN git clone -b v2.4.2 https://github.com/eProsima/Fast-DDS.git \
    && cd Fast-DDS \
    && git clone https://github.com/eProsima/Micro-XRCE-DDS-Agent.git \
    && cd Micro-XRCE-DDS-Agent \
    && mkdir build && cd build \
    && cmake .. \
    && make -j$(nproc) \
    && sudo make install \
    && sudo ldconfig /usr/local/lib/
```

### Simulation Stage
Adding the simulation tools such as Gazebo, ROS2-Gazebo bridges and important ROS2 simulation packages. 

```dockerfile
FROM dev AS simulation
RUN sudo wget ... && sudo apt-get install gz-fortress ...
```

The full installation can be found from lines 85-103.

### PX4 Installation
In this step, all the dependencies needed for PX4 development are installed. These include numerical libraries, PX4 tools and Python packages:

```dockerfile
RUN sudo apt-get install ... && pip3 install pyulog ...
```
The full list is found from lines 108-134. 

Once these dependencies are installed, the PX4 autopilot repository and all its submodules can be cloned. Once that is completed, PX4's own setup script is run to configure everything and PX4 builds the Software-In-The-Loop simulation (SITL).

```dockerfile
WORKDIR /home/ros/PX4-Autopilot
RUN bash ./Tools/setup/ubuntu.sh

RUN make px4_sitl
```

### Custom Gazebo Files & Models
To sync the custom Gazebo with Github in our workspace but still be usable with PX4, the DockerFile creates a link between the necessary PX4-Autopilot directories and the ROS2 workspace so everything can be easily cloned and managed without having to go into the PX4-Autopilot directory and manually change out the files each time. 

```dockerfile
RUN ln -s /home/ros/ros2_ws/Gazebo_files/sim_world.sdf /home/ros/PX4-Autopilot/Tools/simulation/gz/worlds/ && \
    ln -s /home/ros/ros2_ws/Gazebo_files/TU_Delft_logo /home/ros/PX4-Autopilot/Tools/simulation/gz/models/
```

### Final Touch 
This sets the default startup command when the container runs — gives you an interactive shell with ROS sourced under the working directory: `/home/ros/ros2_ws`.

```dockerfile
ENTRYPOINT ["/ros_entrypoint.sh"]
CMD ["/bin/bash"]
```
Now your DockerFile is complete. 

## Creating the devcontainer.json File
To understand the basic configuration of a devcontainer.json, please watch this video before proceeding: \
[![How to create a Dev Container for your project in Visual Studio Code](https://img.youtube.com/vi/DJdMBIQggB0/0.jpg)](https://www.youtube.com/watch?v=DJdMBIQggB0 "How to create a Dev Container for your project in Visual Studio Code")


### Defining the Name and User
Firstly, define the name of your development container – this is what shows up in the VS Code Remote Containers UI.

```json
"name": "Enter-name-here"
```
Define your remoteUser as ros. VS Code will open the container as the ros user instead of root (better for security and simulating a real-world dev environment).

```json
"remoteUser": "ros"
```
Define how the image should be built — using your Dockerfile and passing in the user and group IDs to ensure file permissions work smoothly between your host and container.

```json
"dockerfile": "Dockerfile"
"args": { "USERNAME": "ros", "GID": "1000", "UID": "1000" }

```
### Mapping VS Code project folder
This maps your local VS Code project folder into the container so changes sync instantly. VS Code will "live" in /home/ros/ros2_ws inside the container. This can also change but this is what is defined in the DockerFile as a directory that links directly to the workspace. 
```json
"workspaceFolder": "/home/ros/ros2_ws"
"workspaceMount": "source=${localWorkspaceFolder},target=/home/ros/ros2_ws/,type=bind"

```

### Features & Mounts
You can install handy tools inside the container via a Dev Container Feature. This is allowing terminal commands such as nano and to create virtual environments. 

```json
"features": {
    "ghcr.io/rocker-org/devcontainer-features/apt-packages:1": {
      "packages": "nano,python3-venv,wget,btop"
    }}
```
The mount lets the container access your local SSH keys (read-only) — useful for private repos.

```json
"source=${HOME}/.ssh,target=/home/ros/.ssh,readonly"

```
### `RunArgs`

`RunArgs` sets up system-level permissions and device access needed for simulation, audio, and GUI:

1. Shared memory and host network
2. Audio support (/dev/snd)
3. GUI support (DISPLAY, X11)
4. PX4 simulation privileges (--privileged, SYS_PTRACE)

_**A very important parameter to be aware of is the memory. If your container hangs when trying to build, then it is most likely down to the fact that you didn't allocate enough memory for the building process.**_

```json
"runArgs": [
    "--memory=30g",
    "..."
  ],

```
All our `RunArgs` parameters can be seen on lines 22-34.

### `containerEnv`
These parameters within `containerEnv` are environment variables for different applications such as Gazebo, ROS2 and X11 GUI. 

It has the following functions:
1. Sets simulation paths
2. Enables GUI rendering from container
3. Defines ROS_DOMAIN_ID for DDS communication

```json
"containerEnv": {
    "DISPLAY": "${localEnv:DISPLAY}",
    "DEV_WORKSPACE": "${containerWorkspaceFolder}",
    "..."
    },
```

All our `containerEnv` parameters can be seen on lines 35-42.

### `customizations`
`customizations` installs and configures VS Code extensions for:
1. Python linting
2. C++ & ROS support
3. URDF & XML editing
It also sets default terminal to bash and defines file associations.

```json
"customizations": {
    "vscode": {
      "extensions": [
        "...",
      ],
      "settings": {
        "terminal.integrated.profiles.linux": {
          "bash": {
            "..."
          }
        },
        "terminal.integrated.defaultProfile.linux": "bash",
        "files.associations": {
          "..."
        }
      }
    }
  },

```
All our `customizations` parameters can be seen on lines 43-71.

### `forwardPorts`
This will forward necessary ports into VS Code so PX4, Gazebo, or ROS2 services can talk to your host machine or other tools. These ports can be hard to find but there is one way to do this quickly that I found useful: 
Watch what ports are being opened when you run installed applications such as px4 (make px4_sitl), ros2 launch ..., Gazebo or any web servers or telemetry bridges such as the Micro XCRE-DDS.

```json
"forwardPorts": [
  14550,
  11345,
  6090
]
```
For our example, we have the following ports:

1. `14550` MAVLink: PX4 uses this to communicate with simulators. Protocol used for some uORB topics. 
2. `11345` ROS 2 DDS traffic: Especially for Fast DDS discovery or ROS 2 nodes comm
3. `6090` Used for a GUI, simulator dashboard for PX4/Gazebo configuration.

With all these elements, your devcontainer.json is now complete!

## Final Steps & Remarks 
To build your container, enter VSCode, press F1 and in the dropdown menu, select `Rebuild and Reopen in Container`. On the bottom right of your screen a pop-up should display allow you to access the logs. Building the container takes quite some time so give yourself at least an hour for it to build if it is extensive like ours. 

Furthermore, unfortunately the documentation for building a development container for these specific installations (PX4, ROS2 & Gazebo) are very scarce or are very hard to follow. Therefore, we suggest that you use ChatGPT to find out how to write these files. Especially when it comes to specific details like defining ports.
