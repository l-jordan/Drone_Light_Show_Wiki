The initial version of expanding to multi-drone simulation utilises just a single node, acting on behalf of the entire simulation. This encompasses all of the drones as well as their follower-leader logic. In this case, the path planning is performed on the simulation level, such that the drones will only know their target location in their own coordinate frame. This can be done in a straightforward manner as the relevant topics of all simulated drones are known to the node and the coordinates and their transformations can be performed as a single-loop iteration where the drone name (px4_1, px4_2 ,etc.) is varied in front of the appropriate uORB message.

However, in order to access all of the relevant attributes on each drone, the code features two classes: the drone and the offboard control classes.

The Drone class features the subscribers, publishers and attributes. Although there are some new attributes, the subscribers and publishers are the same as in the single drone case seen in previous wiki chapters.
```powershell
class Drone:
    def __init__(self, node, namespace, qos_profile):
        self.namespace = namespace
        self.node = node
        self.theta = 0.0

        # Publishers
        self.offboard_control_mode_publisher = node.create_publisher(
            OffboardControlMode, f'{namespace}/fmu/in/offboard_control_mode', qos_profile)
        self.trajectory_setpoint_publisher = node.create_publisher(
            TrajectorySetpoint, f'{namespace}/fmu/in/trajectory_setpoint', qos_profile)
        self.vehicle_command_publisher = node.create_publisher(
            VehicleCommand, f'{namespace}/fmu/in/vehicle_command', qos_profile)

        # Subscribers
        self.vehicle_local_position_subscriber = node.create_subscription(
            VehicleLocalPosition, f'{namespace}/fmu/out/vehicle_local_position',
            self.vehicle_local_position_callback, qos_profile)
        self.vehicle_status_subscriber = node.create_subscription(
            VehicleStatus, f'{namespace}/fmu/out/vehicle_status',
            self.vehicle_status_callback, qos_profile)
        self.gps_position_subscriber = node.create_subscription(
            SensorGps, f'{namespace}/fmu/out/vehicle_gps_position',
            self.gps_position_callback, qos_profile)
        
        ######## Global position is not the raw GPS position and is instead the estimated global position based on the
        ######## drone control inputs and a Kalman filter in order to reduce noise
        self.global_pos_subscriber = node.create_subscription(
            VehicleGlobalPosition, f'{namespace}/fmu/out/vehicle_global_position',
            self.global_position_callback, qos_profile)

        # State variables
        self.vehicle_local_position = VehicleLocalPosition()
        self.vehicle_status = VehicleStatus()
        self.global_pos = VehicleGlobalPosition()
        self.coordinate_transform = []  
        self.target_system = self.vehicle_status.system_id
        self.is_landing_triggered = False 
        self.is_disarmed = False 
```

Additionally, the drone class includes the functions required to successfully subscribe to the topics as seen above.

As for the offboard control node itself - the node class starts by establishing the number of available drones and their "namespaces" (the names preceding their uORB topic messages. This allows us to add these names in front of the relevant message and call the same function for all drones in a quick loop. This is established as follows:

```powershell
class OffboardControl_MV(Node):

    def __init__(self) -> None:
        super().__init__('offboard_control_node')

        # Configure QoS profile for publishing and subscribing
        qos_profile = QoSProfile(
            reliability=ReliabilityPolicy.BEST_EFFORT,
            durability=DurabilityPolicy.TRANSIENT_LOCAL,
            history=HistoryPolicy.KEEP_LAST,
            depth=1
        )
        
        namespaces = ['/px4_1', '/px4_2'] #### Expand the list for the desired number of drones
        
        self.vehicles = [Drone(self, namespace, qos_profile) for namespace in namespaces]```
```
The "namespaces" list has to be edited manually to include the appropriate names for the relevant number of drones. Luckily, this follows the same format for all drones if they are launched using the method that will be described later. In the second line for self.vehicles: a drone class is instantiated for all drones that are given in the "namespaces" list. This makes it easy to call various functions and access the drones' attributes later on.

The rest of the Control node features definitions that were already seen in the single-drone application: the arm, disarm, engage_offboard_mode, land and publish_offboard_control_heartbeat_signal. However, there is also a new addition which defines the follower frame transform, which is explained separately in the wiki chapter 2A.
