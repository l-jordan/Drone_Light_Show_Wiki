### QoS Settings Compatibility
Next, the QoS settings need to be established. QoS stands for Quality of Service (QoS) settings. These are like rules you set when subscribing or publishing to a topic to control how reliable, fast and resilient your messages are. These settings determine your:
* Storage history 
* Depth (Only applicable if you're storing last samples and not all)
* Reliability 
* Durability
* Deadline 
* Lifespan
* Liveliness

For a full explanation of what each of these elements mean please refer to the [ROS2 Documentation (QoS settings)](https://docs.ros.org/en/rolling/Concepts/Intermediate/About-Quality-of-Service-Settings.html) 

Now that we understand how QoS settings work for ROS2, we need to make sure that these settings hold for PX4. To subscribe to topics published by PX4, an appropriate QoS setting is needed. The default ROS 2 QoS settings are different from the settings used by PX4 so not all combinations of publisher - subscriber QoS settings are possible. More specifically, the default ROS2 subscriber settings for subscribing are not compatible but for publishing they are. Therefore at the beginning of every node where you will subscribe to a topic, you have to specify the specific QoS settings. 

We didn't find much concrete information about the QoS settings between PX4 and ROS2 but after asking ChatGPT, they gave us the following rule-of-thumb:

1. Best Effort for reliability 
2. Volatile durability as PX4 won't store past messages for us
3. Keep last history
4. Depth is either 1 or 10 so that there is enough buffer for minor delays. 

This transforms to the following in Python code:

```python
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy

qos_profile = QoSProfile(
    reliability=ReliabilityPolicy.BEST_EFFORT,
    history=HistoryPolicy.KEEP_LAST,
    depth=10
)

```
This qos_profile should be put into the __init___ definition which will be presented later. 

It is important to note that since we are using Micro XRCE-DDS middleware, we can only use reliability, durability, history and depth QoS settings and not deadline, lifespan and liveliness. 

### Subscribing & Publishing to Topics
PX4 has specific topics that you can subscribe and publish to. These can be found [here](https://github.com/PX4/PX4-Autopilot/blob/main/src/modules/uxrce_dds_client/dds_topics.yaml). Inside the PX4 flight controller, these topics are referred to as [uORB messages.](https://docs.px4.io/main/en/msg_docs/) which will be used when subscribing to these topics. 

For this example, we want to put the drone into Offboard mode so it can operate autonomously. Then we want the drone to take-off to a specific height. After we want to circle around and land. Let's break it down step-by-step.

Before diving into subscribing and publishing to the topics, the architecture will first be presented. Below you can see that this example uses one node and five topics. These topics first display the uORB messages and the relevant ROS2 topic name underneath. The publisher topics are to request offboard control mode (OffboardControlMode), to publish setpoints (TrajectorySetpoint), and to send vehicle commands such as arming, changing to offboard mode, land, etc. (VehicleCommand). The subscriber topics are to visualise the vehicle setpoints in the local coordinate frame (VehicleLocalPosition) and to see what status the drone currently has, for example, to see if it is armed, in offboard mode, etc. (VehicleStatus).

![ROS2_Architecture drawio](https://github.com/user-attachments/assets/70395ac5-dae7-44fe-abb3-3daf17e0eb0e)

To learn how to use these topics, it is recommended that you first read the following documentation before proceeding: [PX4-Topics:-How-to-Use-Them](https://github.com/p4mars/drone_light_show/wiki/1.A.-PX4-Topics:-How-to-Use-Them).

**1. Creating a Node** \
This is quite straight forward. First import the ROS2 libraries to create a node then create the class and the initialiser definition. Make sure to add your QoS settings here. An example of this can be seen below:

```python
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy

# Node to start autonomous flight
class OffboardControl(Node):
    def __init__(self):
        super().__init__('NODE_NAME')
        
    qos_profile = QoSProfile(
        reliability=ReliabilityPolicy.BEST_EFFORT,
        history=HistoryPolicy.KEEP_LAST,
        depth=10
        )
```

**2. Import the relevant uORB messages from px4_msgs.msg** \
Import the relevant messages in their uORB message format. You can then access the relevant [ROS2 topics](https://github.com/PX4/PX4-Autopilot/blob/main/src/modules/uxrce_dds_client/dds_topics.yaml). 

```python
from px4_msgs.msg import OffboardControlMode, TrajectorySetpoint, VehicleCommand, VehicleLocalPosition, VehicleStatus
```

**3. Initiate the subscribers and publishers** \
This is done in def __init___ using the same format that was presented in the aforementioned documentation about [PX4 topics](https://github.com/p4mars/drone_light_show/wiki/1.A.-PX4-Topics:-How-to-Use-Them).

```python
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy
from px4_msgs.msg import OffboardControlMode, TrajectorySetpoint, VehicleCommand, VehicleLocalPosition, VehicleStatus

# Node to start autonomous flight
class OffboardControl(Node):
    def __init__(self):
        super().__init__('NODE_NAME')
        
    qos_profile = QoSProfile(
        reliability=ReliabilityPolicy.BEST_EFFORT,
        history=HistoryPolicy.KEEP_LAST,
        depth=10
        )

   # Create publishers
    self.offboard_control_mode_publisher = self.create_publisher(
            OffboardControlMode, '/fmu/in/offboard_control_mode', qos_profile)
    self.trajectory_setpoint_publisher = self.create_publisher(
            TrajectorySetpoint, '/fmu/in/trajectory_setpoint', qos_profile)
    self.vehicle_command_publisher = self.create_publisher(
            VehicleCommand, '/fmu/in/vehicle_command', qos_profile)

        
   # Create subscribers
   self.vehicle_local_position_subscriber = self.create_subscription(
            VehicleLocalPosition, '/fmu/out/vehicle_local_position', self.vehicle_local_position_callback, qos_profile)
   self.vehicle_status_subscriber = self.create_subscription(
            VehicleStatus, '/fmu/out/vehicle_status', self.vehicle_status_callback, qos_profile)
```

**4. Create Corresponding Definitions for Each Topic** \
Functions such as arming, disarming, landing, etc. which use the VehicleCommand uORB topic have their own separate definition which calls another generic definition specifically for the VehicleCommand uORB message. To see how this can be built, please refer to the page: [PX4-Topics:-How-to-Use-Them](https://github.com/p4mars/drone_light_show/wiki/1.A.-PX4-Topics:-How-to-Use-Them).

For our specific demo, please refer to lines [52-127](https://github.com/p4mars/drone_light_show/blob/main/src/offboard_control_pkg/offboard_control_pkg/offboard_control.py).

**5. Creating the control loop** \ 
Creating the control loop uses all the previous components together to get the drone moving! To show you how to build the control loop we will be using the definition names used in the [offboard control example](https://github.com/p4mars/drone_light_show/blob/main/src/offboard_control_pkg/offboard_control_pkg/offboard_control.py) to get the drone to take-off, circle and land again at its take-off position.

_1. Starting the timer_ \
The first step is to define the timer. This includes the variable responsible for the time increments and also the timer itself. This variable and command are put in the __init__ definition. In the control loop, the setpoint counter should be updated by dt each time. 

```python
    def __init__(self) -> None:
        ...
        # To count time passed
        self.offboard_setpoint_counter = 0 # To count time passed

        # Create a timer to publish control commands
        # self.create_timer(1/frequency (dt), <control_loop_definiton_name>)
        # In this example the control loop is called timer_callback and is being 
          run at 10 Hz

        self.timer = self.create_timer(0.1, self.timer_callback)

    def timer_callback(self) -> None:
       ...
    
        # Increment counter 
        if self.offboard_setpoint_counter < 1000:  
            self.offboard_setpoint_counter += 1
```

_2. Offboard command switch_ \
Changing into offboard mode requires you to first send offboard command requests via the uORB message OffboardControlMode before sending the command to change to offboard mode via the VehicleCommand uORB message [[1]](https://docs.px4.io/main/en/ros2/offboard_control.html#implementation). 

Therefore, at the beginning of the control loop, the offboard command requests should constantly be sent. This is done using the definition `self.publish_offboard_control_heartbeat_signal()` in our example. In addition to this, for the first 10 seconds, the take-off commands are sent via the `publish_position_setpoint(x, y, z)` definition. 

After 2.5 seconds, we send the offboard mode request to VehicleCommand via the `self.engage_offboard_mode()` definition. Then a second later, we send the command to arm via the `self.arm()` definition. As there is a constant stream of trajectory setpoints from the `publish_position_setpoint(x, y, z)` definition, the drone will arm and take off immediately. 

``` python
 def __init__(self) -> None:
        ...
        # Initialise useful variables 
        self.vehicle_local_position = VehicleLocalPosition()
        self.takeoff_height = -2.0

 def timer_callback(self) -> None:
        # Always maintain offboard heartbeat 
        self.publish_offboard_control_heartbeat_signal()

        # Current altitude 
        current_z = self.vehicle_local_position.z
        
        # ---------------------------------------------------
        # PHASE 1: Initialisation (first 5 seconds)
        # Set the drone to offboard mode and arm it
        # Will takeoff and maintain position for 5 seconds

        # ---------------------------------------------------
        if self.offboard_setpoint_counter < 100:  # ~10 seconds at 10Hz timer
            # Publish setpoint continuously
            self.publish_position_setpoint(0.0, 0.0, self.takeoff_height)
            
            # Engage offboard after 2.5 seconds
            # Sending actual offboard command
            if self.offboard_setpoint_counter == 25:
                self.engage_offboard_mode()
                self.get_logger().info("Offboard mode requested")
                
            # Arm after 3.5 seconds
            # Sending arm command -> Will arm and take off to height proposed by 
            elif self.offboard_setpoint_counter == 35:
                self.arm()
                self.get_logger().info("Arm command sent")
```
_3. Creating the circle trajectory_ \
After a specific time, that we took to be 10 seconds, we started sending the trajectory setpoints via the `self.publish_position_setpoint(x, y, z)` definition for a circle manoeuvre. These setpoints are being sent in the local coordinate frame. To calculate the setpoints, basic trigonometry is used with a specified radius. Once the drone has made a full circle, it enters the landing stage of the flight. 

```python 
 def __init__(self) -> None:
        ...
        # Initialise useful variables 
        self.radius = 1.0
        self.theta = 0

def timer_callback(self) -> None:
  ...

  # ---------------------------------------------------
  # PHASE 2: Circle trajectory
  # ---------------------------------------------------
  if self.offboard_setpoint_counter >= 100:
     if self.theta < 2 * np.pi:

        # Publish circle trajectory
        self.publish_position_setpoint(
           self.radius * np.cos(self.theta),
           self.radius * np.sin(self.theta),
           self.takeoff_height)

        self.theta += 0.1  # Increment theta for circular motion
```

_4. Landing_ \
For the landing we follow a similar procedure as in steps 2 and 3. When the drone has done a full circle, we send trajectory setpoints to go back to the origin via the `self.publish_position_setpoint(x, y, z)` definition. Once it has gotten within a close proximity of the origin, the landing command is sent via the `self.land()` definition which will send the command to the VehicleCommand uORB message. The drone will start to land. Then, when the drone is within half of metre of the ground, the disarming command is sent via the `self.disarm()` definition which sends the disarming command to the VehicleCommand uORB message.
Then the drone disarms and the simulation is finished!

```python 
 def __init__(self) -> None:
        ...
        # Initialise useful variables 
        self.is_landing_triggered = False  # Add to __init__

def timer_callback(self) -> None:
            ...

            # If not less than 2*pi, just hold position
            else:
                # ---------------------------------------------------
                # PHASE 3: Landing
                # ---------------------------------------------------
                self.publish_position_setpoint(0.0, 0.0, self.takeoff_height)
                
                #INITIATE LANDING
                # When the x and y coordinates are less than 0.1 (close enough to the origin), the landing command is sent.
                if self.vehicle_local_position.x < 0.1 and self.vehicle_local_position.y < 0.1:
                    self.is_landing_triggered = True
                    self.land()
                    self.get_logger().info("Landing initiated")

                    # DISARM THE DRONE
                    # Disarming the drone once the drone is within 0.5 metres of the ground. 
                    if current_z > -0.5:  # Within 0.5m of ground (NED frame)
                        self.get_logger().info("Landed successfully")
                        self.disarm()
                        rclpy.shutdown()
```

**6. Creating main**  \
Main consists of the following elements:

* Initialise the ROS2 python client library 
   * `rclpy.init(args=args)`
* Call the offboard control node the create an instance of this class 
   * `offboard_control = OffboardControl()`
* Keeping the node alive and processes callbacks from subscriptions and timers. Without this the node would immediately exit after creation.
   * `rclpy.spin(offboard_control)`
* Properly destroys the node to free resources and shuts down the ROS2 context to stop all communication.
   * `offboard_control.destroy_node()`
   * `rclpy.shutdown()`

Main would look something like this:

```python
def main(args=None) -> None:
    print('Starting offboard control node...')
    rclpy.init(args=args)
    offboard_control = OffboardControl()
    rclpy.spin(offboard_control)
    offboard_control.destroy_node()
    rclpy.shutdown()
```
This is optional but to make sure that your file will only runs when the script is executed directly, include the following if statement, otherwise just call main. 

```python 
if __name__ == '__main__':
    try:
        main()
    except Exception as e:
        print(e)
```

## Setup.bash & Package.xml Files
When you create a package using ROS2, the following will be created [[2]](https://docs.ros.org/en/foxy/Tutorials/Beginner-Client-Libraries/Creating-Your-First-ROS2-Package.html#what-makes-up-a-ros-2-package):
1. package.xml file containing meta information about the package
2. resource/<package_name> marker file for the package
3. setup.cfg is required when a package has executables, so ros2 run can find them
4. setup.py containing instructions for how to install the package
5. <package_name> - a directory with the same name as your package, used by ROS 2 tools to find your package, contains __init__.py

This section will show you how to modify the setup.bash and the package.xml file so your programme runs smoothly. 

### Setup.bash file
This file is very important when it comes to building any sort of ROS2 programme as you will source it each time you want to rebuild your package (make changes to your code). 

The most important components you need to alter in your setup.bash file are: 
* Package name
    * `package_name = 'PACKAGE_NAME`
* Adding your launch file to data files. 
   * `data_files=[('share/ament_index/resource_index/packages',['resource/' + package_name]),('share/' + package_name, ['package.xml']), (os.path.join('share', package_name, 'launch'), ['launch/LAUNCH_FILE_NAME.launch.py'])`
* Required installs -> add px4_msgs  
   * `install_requires`
* Entry point stating where your control node is located 
   * `entry_points={'console_scripts': [ 'offboard_control_node = PACKAGE_NAME_pkg.FILE_NAME:main'],}`

Other aspects you can fill in for completeness are `maintainer_email`, `description` and `license`. The full example of our setup.bash file can be seen below:

```python
from setuptools import find_packages, setup
import os 
from glob import glob

package_name = 'offboard_control_pkg'

setup(
    name=package_name,
    version='0.0.0',
    packages=find_packages(exclude=['test']),
    data_files=[
            ('share/ament_index/resource_index/packages',
                ['resource/' + package_name]),
            ('share/' + package_name, ['package.xml']),
            (os.path.join('share', package_name, 'launch'), ['launch/offboard_control_launch_file.launch.py']),
        ],
    install_requires=['setuptools', 'px4_msgs'],
    zip_safe=True,
    maintainer='ros',
    maintainer_email='l.jordan@student.tudelft.nl',
    description='TODO: Package description',
    license='TODO: License declaration',
    tests_require=['pytest'],
    entry_points={
        'console_scripts': [ 'offboard_control_node = offboard_control_pkg.offboard_control:main'
        ],
    },
)
```

## PX4 Simulation
When PX4 SITL is ran, it will only allow the drone to arm if all the pre-arm checks are met. However, since we are not using a ground station such as QGroundControl, checks will automatically not be passed. To avoid any of these pre-arm checks failing when running the offboard mode node, a parameter file was made specifically to disable these checks. To create this parameter file the following steps were taken:

**1. Run the PX4 simulation as normal**
```bash
cd ..
cd PX4-Autopilot
make px4_sitl gz_x500
```
**2. Once the terminal displays the following:**
```bash
INFO  [px4] Startup script returned successfully
pxh> ...
```
Press enter and input the command (with "pxh>" already provided by the terminal) to disable certain checks:

```bash
param set COM_ARM_WO_GPS 1
param set COM_PREARM_MODE 0
param set NAV_DLL_ACT 0
param set COM_RC_IN_MODE 1
param set EKF2_MAG_TYPE 0
param set SYS_AUTOSTART 1
```
You can change these out with different parameters if needed. 

The following checks used in the example and in the test case are as follows:
1. **COM_ARM_WO_GPS** | Arm without GPS | 1 = allows arming even if GPS lock is not available. 
2. **COM_PREARM_MODE** | Prearm checks | 0 = disables all prearm checks Use with caution — for simulation only!
3. **NAV_DLL_ACT** | Datalink loss action | 0 = do nothing if telemetry is lost. 
4. **COM_RC_IN_MODE** | RC input source | 1 = use MAVLink instead of a physical RC. Allows autonomous operation. 
5. **EKF2_MAG_TYPE** | Magnetometer mode | 0 = no magnetometer fusion. Common in sim where mag data is unreliable or unused.
6. **SYS_AUTOSTART** | Airframe ID | 1 = loads the Generic Multicopter (empty) setup.

**3. Save the file so it can be reused every time you run PX4 SITL.**
```bash
param save /home/ros/<file_name>.params
```
Once this file is created, you can use it each time you run your PX4 SITL instance. Follow steps 1 & 2 but instead of entering the full list of parameters, use:

```bash
param import /home/ros/<file_name>.params
```
